# D4Y Dental Pathway Program — backend

The API for Dentistry for Youth's Dental Pathway Program: a modular, digital program that supports students through the dental school application process. It serves the student portal, the mentor area and the admin pages of the frontend ([d4yfe](https://github.com/ManasKohli/d4yfe)).

**Scope is the pilot cohort only:** about 25 students, a few mentors and 1–2 admins. Don't add features for the full launch.

**Status:** build step 0 (task T1) is done: TypeScript, lint, tests, the folder skeleton, `GET /health`, the Dockerfile and CI. No feature code yet; auth, the database and `/me` come next (step 1). Every design decision, with the reasoning behind it, is in [`docs/architecture.md`](docs/architecture.md). Read that before changing anything structural.

## How it fits together

| Part | Technology | Where |
|---|---|---|
| Frontend | React + Vite | `d4yfe` repo: production on Firebase Hosting in this API's GCP project; Vercel for dev and previews only (plan D41) |
| API | Node.js 24 + Express 5 + TypeScript | This repo, deployed on Google Cloud Run |
| Database, auth, file storage | Supabase (Postgres, Auth, Storage) | Supabase projects in `ca-central-1` |
| Payments | Stripe Checkout (hosted, cards only) | Stripe account |

```
 Browser (d4yfe)
   │  sign in / sign up ──────────────────────►  Supabase Auth
   │  API calls with the Supabase access token
   │  file uploads straight to Storage (signed URL from the API)
   ▼
 Express API (Cloud Run)
   ├─ verifies the token against Supabase's public keys (JWKS)
   ├─ reads and writes Postgres through the Supabase shared pooler
   ├─ issues short-lived Storage upload/download links
   └─ creates Stripe Checkout Sessions; receives Stripe webhooks
```

- **Supabase Auth** handles accounts, passwords, email verification and resets. The frontend talks to it directly.
- **This API is the only thing that reads or writes app data.** Row Level Security is on for every table with no policies, so the frontend's publishable key can't read tables.
- **Program content stays in the frontend** (`d4yfe/src/data/`). The database holds only the module and chapter slugs and the rubric criteria, in the seeded `program_modules` table.

## Project structure

The code is organised by feature. Each module owns its routes, rules and SQL, and every router is mounted in `src/routes/index.ts`. ESLint enforces the layering (`src/modules/README.md`). Layout:

```
src/
  server.ts                start the server, graceful shutdown on SIGTERM
  app.ts                   build the Express app and its middleware
  routes/index.ts          route registry: every feature router is mounted here
  config/env.ts            zod-checked environment variables
  db/
    client.ts              postgres.js pool (shared pooler, prepare: false)
    database.types.ts      generated by `supabase gen types typescript`; do not edit
  lib/                     logger.ts, http-logger.ts; later supabase.ts (Storage + Auth admin), stripe.ts
  middleware/              auth.ts, require-role.ts, validate.ts, error-handler.ts
  errors/app-error.ts
  types/express.d.ts       req.user typing
  modules/
    health/                GET /health (step 0)
    me/  student/  mentor/  admin/  payments/   (added step by step)
      <name>.routes.ts       HTTP: parse, validate, call the service, respond
      <name>.service.ts      rules: who may do what, status computation
      <name>.repository.ts   SQL only
      <name>.schemas.ts      zod request and response shapes
      <name>.test.ts         unit tests for the service
    access/                the only writer of enrollments and credit_ledger
tests/                     integration tests (supertest + local Supabase)
supabase/                  migrations/, seed.sql, config.toml
docs/architecture.md       the reviewed plan and decision log
```

## Conventions

- **Dependencies point one way:** `routes → service → repository → db`. Routes never run SQL, and repositories never make decisions.
- **One owner per table.** A module never imports another module's repository. To change a student's access or credits, call `access.service` (`grantProduct`, `grantModule`, `useCredit`) inside your own transaction.
- **Every input is validated with zod** at the route. Every response has a zod schema, which is the API contract: the frontend generates its types from `openapi.json`.
- **One error shape:** `{ "error": { "code": "...", "message": "...", "details"?: ... } }`. `details` is present only when it helps the caller fix the request: for `validation_failed` it is a list of `{ path, message }`. Throw `AppError`; the error handler maps Postgres unique and foreign-key violations to 409 and 400, and hides anything unexpected behind a generic 500.
- **SQL is always parameterised** (postgres.js tagged templates). Every repository query is covered by an integration test, because the generated types don't check SQL.
- **Times are `timestamptz` in UTC.** The frontend shows them in the viewer's time zone.
- **Never log** request bodies, submission text, tokens or keys.
- **Keep it small.** Build for the pilot, and delete code a change makes unused.

## Getting started

> Today (step 0) only `npm install`, `cp .env.example .env` and `npm run dev` are needed. The Supabase and Stripe steps apply from step 1 onwards.

Requires Node 24 (`nvm use`), Docker (for the local Supabase stack), the [Supabase CLI](https://supabase.com/docs/guides/cli) and the [Stripe CLI](https://docs.stripe.com/stripe-cli).

```sh
npm install
cp .env.example .env          # fill in values from the local Supabase output
supabase start                # local Postgres, Auth and Storage in Docker
supabase db reset             # apply migrations and seed.sql
npm run dev                   # API on http://localhost:8080
stripe listen --forward-to localhost:8080/webhooks/stripe   # in a second terminal
```

Scripts (`openapi` and `db:types` arrive with the first schemas and migrations):

```sh
npm run dev        # watch mode
npm run typecheck  # tsc, strict
npm run lint       # ESLint
npm run test       # Vitest (unit + integration against local Supabase)
npm run build      # compile to dist/
npm run openapi    # write openapi.json from the response schemas
npm run db:types   # regenerate src/db/database.types.ts after a migration
npm run check      # typecheck, lint, test, build; run before every push
```

## Environment variables

| Name | Where | What |
|---|---|---|
| `DATABASE_URL` | Secret | Supabase **shared pooler**, transaction mode: `aws-*-ca-central-1.pooler.supabase.com:6543`. The direct host is IPv6-only, and Cloud Run can't reach it by default |
| `SUPABASE_URL` | Secret | Project URL; the JWKS endpoint is derived from it |
| `SUPABASE_SECRET_KEY` | Secret | `sb_secret_…` key, for Storage and Auth admin only |
| `STRIPE_SECRET_KEY` | Secret | Test mode until launch |
| `STRIPE_WEBHOOK_SECRET` | Secret | From the Stripe dashboard, or from `stripe listen` locally |
| `APP_URL` | Plain | Frontend URL, for Checkout success and cancel redirects |
| `ALLOWED_ORIGINS` | Plain | Comma-separated CORS allowlist of bare origins (`https://app.example.com`, no path or trailing slash; startup refuses anything else). Production: the pilot domain (and the Firebase `*.web.app` / `*.firebaseapp.com` URLs if used), never Vercel origins. Dev/staging: Vercel preview origins and `http://localhost:5173` (plan section 8) |
| `PORT` | Set by Cloud Run | Defaults to 8080 locally |
| `NODE_ENV` | Plain | `production` by default (and in the image). `.env.example` sets `development` for pretty local logs |
| `LOG_LEVEL` | Plain | pino level, default `info` |

The app refuses to start if any variable is missing or malformed (`src/config/env.ts`). Never commit `.env`. Only this API holds the Supabase secret key; the frontend uses the publishable key.

## API

Every route except `/health`, `GET /products` and `/webhooks/stripe` needs a Supabase access token (`Authorization: Bearer …`) and checks the caller's role.

| Area | Routes |
|---|---|
| Public | `GET /health`, `GET /products` |
| Me | `GET /me`, `POST /me/onboarding` |
| Student | `/student/home`, `progress`, `assignments`, `assignments/:id/upload-url`, `assignments/:id/submissions`, `feedback`, `feedback/:id`, `sessions`, `resources`, `resources/:id/download`, `schools` |

The full list, with methods and the rules behind each flow (checkout seat holds, webhook transaction, review credits), is in [`docs/architecture.md`](docs/architecture.md) sections 4–6.

## Database

Postgres on Supabase. Migrations live in `supabase/migrations/` and are the only way the schema changes; never edit tables in Studio by hand. The exception is pilot reference data (`schools`), which admins edit in Supabase Studio.

- **Two projects:** dev/staging on the Free plan, production on **Pro** (never paused, daily backups kept 7 days).
- **RLS is on for every table, with no policies.** A new table without RLS is a bug.
- **Index every foreign key you filter on.**
- After each migration, run `npm run db:types` and `npm run openapi` if response shapes changed.

Main tables: `program_modules`, `profiles`, `invites`, `student_profiles`, `mentor_profiles`, `cohorts`, `products`, `product_modules`, `orders`, `stripe_events`, `enrollments`, `credit_ledger`, `chapter_progress`, `assignments`, `submissions`, `reviews`, `events`, `volunteer_hours`, `resources`, `schools`. Columns and rules are in `docs/architecture.md` section 4.

## Deployment

The API runs on **Google Cloud Run** in `northamerica-northeast2` (Toronto) or `northeast1` (Montréal), next to Supabase `ca-central-1`, so student data stays in Canada.

- Multi-stage Dockerfile (`node:24-slim`), running as a non-root user
- Min instances 0, max 3, 512 MB, concurrency 80
- Secrets come from Secret Manager; nothing secret is baked into the image
- GitHub Actions: CI runs `npm run check` on every PR. Deploy pushes the image to Artifact Registry and deploys to Cloud Run, authenticating with Workload Identity Federation (no service account keys in GitHub)
- Cost guards: a billing budget alert, max 3 instances, an Artifact Registry cleanup policy, and the Supabase spend cap left on

**One-time setup:** turn on asymmetric JWT signing keys in each Supabase project, set up custom SMTP for Auth emails, and create the first admin (invite them from the Supabase dashboard, then set `profiles.role = 'admin'` in Studio).

## Not in the pilot

In-app booking (mentors share scheduling links), in-app hardship applications (a form plus an admin grant), scheduled jobs and reminder emails, delayed payment methods, and package upgrades. The reasons, and when to revisit each, are in [`docs/architecture.md`](docs/architecture.md).
